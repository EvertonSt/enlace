2. PROJECT STRUCTURE NOTES
--------------------------------------------------------------------------------
  enlace is a pnpm monorepo. The mobile app is at apps/mobile (Expo SDK 53,
  React Native 0.79.7, React 19). Native android/ is generated by `expo prebuild`.
  pnpm uses ABSOLUTE symlinks in node_modules/.pnpm — so MOVING the folder breaks

    apps/mobile/app/............ Expo Router screens (index=login, dashboard,
                                 outages, tickets, billing, settings)
    apps/mobile/src/lib/........ auth.tsx, ThemeContext.tsx, theme.ts, cache.ts, i18n.ts

    apps/mobile/src/components/. AnimatedSplash.tsx
    apps/mobile/android/........ generated native project (gradlew lives here)

3. THE #1 LESSON: LONG PATHS + SPACES BREAK ANDROID BUILDS
--------------------------------------------------------------------------------
  The original repo path was:
     C:\AI\Freebuff Desktop\GitHub Projects\enlace\apps\mobile
  That path is LONG and contains SPACES. This alone caused problems #1 and #2.

  Windows has LongPathsEnabled=1, BUT CMake/ninja enforce their OWN ~250-char
  limit on intermediate object paths. With pnpm's deep
  node_modules/.pnpm/...expo-modules-core.../... paths, the build hits that
  limit and ninja loops forever ("manifest still dirty after 100 tries").

  FIX (the master fix): build from a SHORT, NO-SPACE path.
     C:\m\apps\mobile     (copy of apps/mobile)
  Everything below assumes you work from C:\m, not the original long path.

  How to create C:\m (preserve symlinks by COPYING, then reinstalling):
     - Copy the apps/mobile tree to C:\m (any method; symlinks get dereferenced).
     - Put a ROOT package.json + pnpm-workspace.yaml + pnpm-lock.yaml at C:\m
       (copied from the original enlace repo root) so pnpm resolves the
       workspace correctly.
     - Reinstall with the project's pnpm (see recipe in section 12).

  Do NOT try: robocopy (Access denied), move (symlink alias breaks), or
  editing CMakeLists CMAKE_OBJECT_PATH_MAX (no-op — ninja ignores it).

4. PROBLEM #1 — ninja: "manifest 'build.ninja' still dirty after 100 tries"
--------------------------------------------------------------------------------
  Symptom: Gradle :app:buildCMakeRelWithDebInfo[arm64-v8a] never finishes;
           ninja reports the manifest is still dirty after 100 tries.
  Root cause: a generated .o / .ninja path exceeded CMake/ninja's ~250-char
           limit because of the deep node_modules/.pnpm path under the long
           project directory.
  Fix: relocate to C:\m (short, no-space). After that, native compile finishes.
  Lesson: if you EVER see a ninja "still dirty" loop on a React Native build,
          suspect path length first, not your code.

5. PROBLEM #2 — Hermes compiler path split on the space
--------------------------------------------------------------------------------
  Symptom: during JS bundle compile, the Hermes compiler errors out because its
           executable path contained a space ("C:\AI\Freebuff Desktop\..." ) and
           the shell split it.
  Root cause: same long/spaced path as #1.
  Fix: the short C:\m path removes the space, so hermesEnabled=true works.
  Note: at one point hermesEnabled was toggled to false to dodge this — that is
        NOT needed once you are on a short path. Keep hermesEnabled=true.

6. PROBLEM #3 — expo-router/entry resolves to the MONOREPO root
--------------------------------------------------------------------------------
  Symptom: Gradle's JS bundle step fails with
           "Unable to resolve module expo-router/entry ... from C:\...\enlace/."
  Root cause: without ENTRY_FILE, Metro walks UP from the expo-router symlink
           target and treats the monorepo root as the Expo project root, so it
           bundles the wrong entry and can't find app/ screens.
  Fix: export ENTRY_FILE=node_modules/expo-router/entry.js before the build.
           This anchors the bundle entry inside apps/mobile regardless of
           symlinks. Works even if a root package.json is present at C:\m.
  (A one-line edit to android/app/build.gradle adding `react { root = file("../../") }`
   was tried and found UNNECESSARY at the short path — do not add it.)

7. PROBLEM #4 — Java compile: cannot find symbol expo.core.ExpoModulesPackage
--------------------------------------------------------------------------------
  Symptom: :app:compileReleaseJavaWithJavac fails:
           "cannot find symbol ... expo.core.ExpoModulesPackage"
  Root cause: a STALE android/build/generated/autolinking/autolinking.json
           (and the PackageList.java it generates) was copied from an OLD
           prebuild. It imported the class as `expo.core.ExpoModulesPackage`,
           but the CURRENT expo@53 ships the class as `expo.modules.ExpoModulesPackage`
           (package expo.modules). The two names don't match -> symbol not found.
  Fix: delete the stale generated files so the autolinking CLI regenerates them
           against the installed expo:
             del apps\mobile\android\build\generated\autolinking\autolinking.json
             del apps\mobile\android\app\build\generated\autolinking\src\main\java\
                 com\facebook\react\PackageList.java
           (A fresh `expo prebuild --platform android --no-install --clean`
            also regenerates these. After a clean prebuild from C:\m the autolinking
            is correct, so this delete is mainly needed if you COPY an android/
            folder around.)
  How we confirmed the root cause: grepped the expo source
           (node_modules/expo/android/src/main/java/expo/modules/ExpoModulesPackage.kt)
           -> it declares `package expo.modules`. So the autolinking JSON must say
           `expo.modules.ExpoModulesPackage`, not `expo.core`.

8. PROBLEM #5 (RUNTIME CRASH) — "Incompatible React versions"
--------------------------------------------------------------------------------
  Symptom: app INSTALLS and launches, but immediately shows a red crash:
           JavascriptException: Incompatible React versions:
             react: 19.2.8   vs   react-native-renderer: 19.0.0
           (react-native@0.79.7 bundles react-native-renderer 19.0.0 and enforces
            an EXACT match with react.)
  Root cause: apps/mobile/package.json declared "react": "^19.1.0", which pnpm
           resolved to 19.2.8. react-native@0.79.7 requires react === 19.0.0.
           This is a PRE-EXISTING bug in the project (the original enlace repo
           has the same "^19.1.0" — it would have crashed identically; it was
           just never caught because no local APK was built before).
  Fix:
     a) In apps/mobile/package.json set exactly:
          "react": "19.0.0",
          "react-dom": "19.0.0"
     b) In pnpm-workspace.yaml add overrides so EVERY transitive copy matches:
          overrides:
            react: 19.0.0
            react-dom: 19.0.0
     c) Reinstall (pnpm install --no-frozen-lockfile) with the project's pnpm 9.15.5.
     d) Rebuild. Crash gone — process stays alive (verified PID alive 12s+).
  Lesson: React Native pins react to an EXACT version via its renderer. Never let
          react float to a newer patch than react-native's renderer. If you bump
          react-native, also bump react to the version its renderer expects.

9. UI FIX #1 — Language inconsistency (English leaks into PT-BR)
--------------------------------------------------------------------------------
  Symptom: in Português (BR), most of the app was Portuguese but some strings
           stayed English: the Settings section labels (Account/Appearance/
           Security/Storage) and the login biometric card ("Login with
           Fingerprint", "Touch the sensor to authenticate", "or sign in with
           password").
  Root cause: those strings were HARDCODED in English in the TSX, not run through
           the i18n function t(). (Settings also hardcoded the theme/language
           option button labels "System/Light/Dark"/"English/Português (BR)".)
  Fix:
     - Added keys to src/i18n/en.json and src/i18n/pt-BR.json:
         settings.account / settings.appearance / settings.security /
         settings.storage / settings.cachedData / settings.cached /
         settings.clear / settings.enabledTouch / settings.disabled /
         settings.clearCacheTitle|Body|Done|DoneBody /
         settings.biometricLogin / settings.biometricDisabledTitle|Body /
         settings.credentialsNeededTitle|Body
         auth.biometricLogin / auth.biometricSub / auth.authenticating /
         auth.orPassword / auth.biometricFailed / auth.biometricExpired /
         auth.enableBiometricTitle|Body / auth.biometricEnabled
     - Routed ALL of them through t() in:
         app/settings.tsx  (section labels, option buttons, biometric desc,
                            cache label, clear-cache & biometric & logout alerts)
         app/index.tsx     (biometric card title/sub, divider, and the enable/
                            failed alerts)
  Lesson: NEVER hardcode user-visible strings. Even "Account" and "System" must
          go through t(). The i18n JSON files are the single source of truth.

10. UI FIX #2 — "Chamados de Suporte" header clipped by the + Novo Chamado button
--------------------------------------------------------------------------------
  Symptom: on the Support Tickets screen the heading "Chamados de Suporte" was
           cut off at the right edge (the long Portuguese title overlapped the
           "+ Novo Chamado" button).
  Root cause: the header row is flexDirection:row with justifyContent:space-between
           and the title Text had NO flex/shrink, so a long title overflowed and
           the button overlapped it.
  Fix: in app/tickets.tsx, the title style became:
         title: { fontSize:24, fontWeight:'bold', color:..., flex:1, flexShrink:1,
                  marginRight:8 }
           (flexShrink lets the title yield space to the button instead of being
            clipped.) Also added flexShrink:1 to dashboard.tsx and outages.tsx
           titles as a safeguard for their longer Portuguese headings.
  Verified on device: "Chamados de Suporte" fully visible, "+ Novo Chamado"
           beside it with no overlap.

11. UI FIX #3 — Dark theme only styled the chrome (top bar + nav)
--------------------------------------------------------------------------------
  Symptom: selecting Dark in Settings turned the header and bottom nav dark, but
           the whole CONTENT area (cards, background) stayed white.
  Root cause: every screen computed `const dark = useColorScheme() === 'dark'`,
           which reads the SYSTEM dark mode, IGNORING the user's manual theme
           preference. Meanwhile the header/nav used useTheme().isDark (the user
           preference). So with phone in System/Light but app set to Dark, the
           chrome went dark and the screens stayed light.
  Fix: make the user preference the single source of truth.
     - src/lib/theme.ts: useThemeColors() now returns dark from useTheme().isDark
       (the ThemeContext preference), not useColorScheme().
     - Switched EVERY screen from `useColorScheme()` to the context:
         app/index.tsx, app/settings.tsx, app/tickets.tsx, app/dashboard.tsx,
         app/billing.tsx, app/outages.tsx  ->  const { isDark: dark } = useTheme();
         src/components/AnimatedSplash.tsx  ->  const { isDark: dark } = useTheme();
       and removed useColorScheme from the react-native imports.
     (ThemeContext.tsx itself still uses useColorScheme ONLY as the "system"
      fallback when preference==='system' — that is correct and intended.)
  Verified on device: with Dark selected, the entire Settings AND Support Tickets
           screens render dark navy (background + cards + text).

13. GOTCHAS / "NEXT TIME" CHECKLIST
--------------------------------------------------------------------------------
  [ ] Project path has a space or is > ~120 chars? -> build from a short
      no-space copy (C:\m). Don't fight it.
  [ ] Use the PROJECT's pnpm (9.15.5), not a newer global one. Mismatched pnpm
      re-resolves the lockfile and silently skews package versions.
  [ ] Always `cd .../android` before `./gradlew` (gradlew is NOT at apps/mobile).
  [ ] Set ENTRY_FILE=node_modules/expo-router/entry.js for the bundle step.
  [ ] JAVA_HOME must be a native Windows path (backslashes), not /c/Users/...
  [ ] adb paths must be native Windows (C:/...), not /c/... (native exe can't
      translate MSYS paths).
  [ ] React version must EXACTLY match react-native's renderer. Don't float react
      with ^ when RN pins it.
  [ ] If Java says "cannot find symbol expo.core.X": delete the stale
      autolinking.json + PackageList.java and let prebuild regenerate them.
  [ ] Don't be alarmed that the APK's res/ files are OBFUSCATED names (_p.png,
      13.webp) — aapt2 resource obfuscation renames them; resources.arsc still
      maps ic_launcher etc. The icon IS bundled.
  [ ] Theme: source `dark` from the user-preference context, NOT system
      useColorScheme(), or dark mode will only paint the chrome.
  [ ] Never hardcode user-visible strings — route everything through t().
  [ ] Header rows with a title + action button: give the title flex:1,
      flexShrink:1 so long localized titles don't get clipped.
  [ ] pnpm symlinks are absolute — a MOVE breaks them; COPY + reinstall instead.
  [ ] Never preserve credentials in code/notes. EXPO_PUBLIC_API_URL is a non-secret
      URL and is safe to bake in; actual login secrets are not.
